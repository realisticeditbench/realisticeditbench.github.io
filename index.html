Motivation

Why Incremental Code Editing?

LLMs have shown strong performance in code generation, but in real software development, editing existing code is far more common — roughly 70% of commits involve code edits rather than writing new code from scratch.

Real editing is incremental: developers apply a sequence of logically ordered changes, where each step builds on prior modifications. Models must predict subsequent edits from partial history, not just translate a requirement into a one-shot patch.

Requirement-based benchmarks

SWE-Bench, CanItEdit, etc. generate edits from textual requirements only — omitting prior edit context central to real workflows.

Incremental benchmarks

CoEdPilot, TRACE randomly sample prior hunks, breaking logical order; target edits are 2–3 lines; metrics measure text overlap, not functional correctness.

Our goal

Evaluate whether models can continue real development trajectories — with sequential prior edits, project-level context, and test-based validation.

Introduction

What is RealisticEditBench?

RealisticEditBench evaluates LLMs on incremental code editing tasks from GitHub pull requests across 12 well-maintained Python repositories. Each PR is manually decomposed into ordered sub-edits; models receive a prefix as prior-edit context and must predict the remaining edits.

Given a codebase, optional task description, and prior edit history, the model generates a patch validated by executable test cases — complementing SWE-Bench's requirement-driven evaluation.

📚 Related Work

Requirement-Based Benchmarks

LLMs generate modified code from requirements without prior edit history:

  • SWE-Bench — issue/PR-driven bug fixing with tests
  • CanItEdit, EditEval, CodeEditorBench — hand-crafted or commit-based
  • NoCode-Bench, PeacExec — feature/efficiency-driven edits

Incremental Benchmarks

LLMs leverage historical edits, but with key limitations:

  • Random prior selection — CoEdPilot, TRACE violate logical edit order
  • Short targets — typically 2–3 lines per edit hunk
  • Similarity metrics — exact match, BLEU; no functional validation

Four Decomposition Principles

Context Coherence

Contiguous code regions; minimize cross-file jumps.

Atomic Intent

Each sub-edit = one core editing intent.

Logical Dependency

Subsequent edits build on earlier ones.

Cognitive Load Stratification

Low-load ops → prior edits; high-load reasoning → targets.

📊 Experimental Results
RQ1

LLM Performance

Even with oracle context, resolved rates stay below 30%. Combined prompt outperforms single-source prompts.

RQ2

Prior-Edit Amount

More history → higher resolved rate. Claude-Sonnet-4.5: 17.98% (20%) → 50.28% (80%).

RQ3

Advanced Methods

SWE-Agent improves all LLMs (+7.87%–20.50%). Prior-Edits-Only is a distinct, harder capability than Requirement-Only.

RQ4

Task Types

Single-file > multi-file. Bug repair (43.62%) > feature addition (24.48%) for SWE-Agent+Claude.

RQ5

Failure Analysis

Three failure modes: intent ambiguity from sparse history, mistaking edit patterns for intent, and missing repository-level propagation.

💡 Implication
Optimize Context

Supplement edits with brief intent descriptions; richer prior-edit context helps refactoring and feature addition.

Rational Cursor Usage

Tab suits repetitive local edits; complex changes need capable LLMs with manual verification.

Editing-Specific Agents

Adapt SWE-Agent for cross-file editing, prior-edit signals, and reduce iteration steps.

Real-Time Non-Agent Design

Use static analysis and prompt engineering for Tab-based assistants where latency matters.

⚙️ Evaluation Harness

Docker-based reproducible evaluation per task instance.

  • Does not support Windows
  • Recommended: Ubuntu 22.04 x86_64
  • Minimum: 120GB storage, 16GB RAM, 8 CPU cores
python -m editbench.evaluation.run_evaluation run \
    --dataset_name "all" \
    --predictions_path 'gold' \
    --max_workers 2 \
    --run_id "0.2"
🚀 Quick Start & Usage 
git clone https://github.com/Anonymity-hub/RealisticEditBench.git
cd RealisticEditBench
pip install -e .

python -m editbench.inference.run_api \
    --model gpt-5-codex \
    --dataset_name all \
    --run_id "0.2"

python -m editbench.evaluation.run_evaluation run \
    --dataset_name "all" \
    --model gpt-5-codex \
    --max_workers 2 \
    --run_id "0.2"
